3. TRE DIVERGENZE DAL PIANO, RILEVATE E RISOLTE
--------------------------------------------------------------------------------

[A] "Sostituire SHA-256 con Swarm" avrebbe rotto la notarizzazione.

    src/Ancorhash.Core/Services/NotarizationService.cs:27-32 impone una regex
    stretta: document_hash deve essere SHA-256 hex di 64 caratteri. Una
    reference Swarm con encrypt:true è di 128 caratteri (32 byte indirizzo +
    32 byte chiave). Ogni notarizzazione avrebbe risposto 400.

    In più il brief Arkiv prescrive esattamente l'opposto (manual/prizes.md:42):
      "leave the file where it is and put an Arkiv entity beside it,
       a hash, a URL or a CID"

    DECISIONE: SHA-256 mantenuto come ancora di integrità; Swarm aggiunto
    come campo parallelo. Nessuna modifica al backend in Fase 1.

[B] Swarm ID non è una funzione pura: è un client con stato di connessione.

    API reale verificata sui typings v0.4.0 (non sulla documentazione):
      new SwarmIdClient({iframeOrigin, metadata, onConnectionChange})
      await client.initialize()      // monta un iframe nascosto
      await client.connect()         // passkey o account Ethereum
      await client.uploadData(bytes, {encrypt:true}) -> {reference}
      client.destroy()               // il client NON è riutilizzabile dopo

    Punto critico: ConnectionInfo.canUpload resta FALSE anche con identità
    connessa, se l'utente non ha postage stamp e non è configurato un gateway
    sovvenzionato. È lo stato più frequente prima di riscattare un gift code.

    DECISIONE: lo stato di connessione vive in App.tsx, non in hash.ts.

[C] expiration_days non permette di dimostrare Arkiv Mission 02.

    manual/prizes.md:68 — "Keep lifetimes at seconds or a couple of minutes,
    because nobody can wait on Sunday morning."

    Con la sola unità "giorni" nessun giudice vedrebbe mai un record scadere.

    DECISIONE: il campo inviato è expiration_seconds (unità esplicita nel
    nome), con input in giorni per il prodotto reale + preset demo da 60s.

Da official/typescript-sdk/mutating-data:

  Entità   = payload + contentType (MAI indicizzati, max 128 KiB)
           + attributes (max 30, tipizzati, indicizzati)
           + expires (altezza di BLOCCO, non secondi)
  engine   -> key (32 byte), owner, creator, createdAt, updatedAt, expiresAt
  Nomi attributo: 1-32 ASCII, minuscola iniziale, poi [a-z0-9._-], snake_case.
  Riservati: prefisso $, sequenza --, e le parole and/or/not/true/false/
  startswith/exists/typeof + i tag di tipo.

  TIPI E OPERATORI (da @arkiv-network/sdk/attr):
    str      <=128 byte UTF-8      eq, startsWith
    bool                           eq
    i32      -2^31 .. 2^31-1       eq, range
    u64      0 .. 2^64-1           eq, range
    u256     0 .. 2^256-1          eq, range
    dec      decimale <=18 cifre   eq, range
    addr     20 byte               eq
    key      32 byte entity key    eq
    bytes32  32 byte qualsiasi     eq

  Solo i quattro tipi numerici hanno indice ordinato. Un numero salvato come
  str supporta solo eq e prefisso. I valori vanno SEMPRE avvolti nel
  costruttore: eq("seller", str(...)) e eq("seller", addr(...)) sono domande
  diverse e solo quella col tipo giusto trova l'entità.

Da official/json-rpc/mutating-entities:

  Precompile Arkiv : 0x4400000000000000000000000000000000000044 (uguale su
                     ogni chain Arkiv)
  BLOCK TIME       : 2 SECONDI      <-- serve per expiration_seconds -> blocchi
  Transaction value: 0
  Calldata         : execute((uint8 operation, bytes operationData)[] ops)
                     selector 0x49650044, batch atomico e ordinato
  Tag operazioni   : 1 Create, 2 Patch, 3 Extend Expiry,
                     4 Transfer Ownership, 5 Delete
  Create struct    : (uint128 salt, uint64 expiresAt, uint64 minLifetime,
                      uint8 creationFlags, Attribute[] attributes)
                     expiresAt = blocco assoluto di scadenza

CONSEGUENZA DI PROGETTO: expiration_seconds deve essere convertito in
blocchi (secondi / 2) e sommato al blocco corrente per ottenere expiresAt.
Il preset demo da 60 s corrisponde a ~30 blocchi.

B5. STEP 1 — DECISIONE DI ARCHITETTURA (PROPOSTA, in attesa di review)
--------------------------------------------------------------------------------

Opzioni valutate:

(a) C# puro via Nethereum
    FATTIBILE, e più di quanto sembrasse: il protocollo è documentato per
    intero (precompile, selector, struct). Nethereum sa mandare quella
    transazione.
    COSTO: va codificato a mano Attribute[] per tutti e nove i tipi e va
    reimplementato anche il lato query, senza rete di sicurezza. La pagina
    ufficiale stessa dice "Most developers should use the TypeScript SDK
    instead of raw transactions".
    RESA PER IL PUNTEGGIO: nessuna. Arkiv valuta "Why Arkiv" e "Technical
    execution", non la reimplementazione dell'SDK in C#.
    -> Scartata per rischio/tempo, non per impossibilità.

(b) Azure Function TypeScript per le sole scritture
    SDK ufficiale, rischio basso, modello gas-sponsored intatto.
    Ma anche le letture passerebbero dal backend: un hop in più, e la prova
    della Mission 02 (stessa query prima/dopo la scadenza) diventa goffa da
    mostrare.

(c) IBRIDO: scritture firmate dal relayer (TS) + query in sola lettura dal
    frontend React                                      <-- RACCOMANDATA
    - Scritture: SDK ufficiale, lato server, firmate dal relayer. Gas
      sponsorizzato, owner delle entità coerente, l'utente non ha bisogno di
      un wallet (coerente con l'attuale MOCK_WALLET_ADDRESS).
    - Letture: public client direttamente da React verso l'RPC Tiramisu.
      Nessun hop, e soprattutto la prova della Mission 02 gira DAL VIVO
      nella UI davanti ai giudici: è esattamente ciò che la mission chiede.
    - Predispone anche la Mission 03 (subscribe via websocket), se la
      vorremo.

    TRADE-OFF DA DICHIARARE, non da nascondere:
    - Due runtime: .NET per la notarizzazione, Node per Arkiv.
    - Owner delle entità = wallet del relayer. Quindi "org" è DICHIARATO,
      non dimostrato dalla firma. Va scritto nello schema.
    - L'access key NON va nel frontend: finirebbe nel bundle. Il frontend
      usa l'RPC pubblico rate-limited; l'access key resta lato backend.

Friction registrata: F-07 (nessun SDK .NET). Non è un bug, è un gap, ed è
quello che ha spostato l'architettura.
